# Security Group Alert — Incident Response Runbook

## Purpose

This runbook defines the response process for security alerts generated by the AWS Cloud Security Monitoring Lab.

The monitoring system detects changes to EC2 Security Groups through AWS CloudTrail and Amazon EventBridge. AWS Lambda analyzes the event and Amazon SNS notifies the security analyst.

The goal of this runbook is to provide a consistent process for investigating and responding to potentially unauthorized or dangerous Security Group changes.

---

## Alert Information

A security alert may contain:

- Severity level
- AWS API action
- Security Group ID
- AWS Region
- Identity responsible for the change
- Event timestamp
- Recommended action

Alerts are currently classified as **MEDIUM** or **HIGH** severity.

---

## Severity Levels

### HIGH

A HIGH-severity alert indicates potentially dangerous public network exposure.

Examples include:

- SSH (TCP 22) opened to `0.0.0.0/0`
- RDP (TCP 3389) opened to `0.0.0.0/0`

These configurations can expose administrative services to the public internet and should be investigated immediately.

### MEDIUM

A MEDIUM-severity alert represents another monitored Security Group modification that does not match the current HIGH-severity detection criteria.

Examples include:

- Adding an inbound rule from a restricted IP range
- Removing an inbound rule
- Adding an outbound rule
- Removing an outbound rule

MEDIUM alerts should still be reviewed to verify that the change was authorized.

---

## Investigation Procedure

### 1. Review the Alert

Review the SNS notification and identify:

- What Security Group changed?
- What API action occurred?
- Who performed the action?
- When did the change occur?
- What AWS Region was affected?
- What severity was assigned?

### 2. Review the Security Group

Open the AWS EC2 console and locate the Security Group identified in the alert.

Review:

- Inbound rules
- Outbound rules
- Open ports
- Allowed IP ranges
- Associated AWS resources

Determine exactly what changed.

### 3. Validate the Identity

Use AWS CloudTrail to investigate the API event.

Confirm:

- IAM user or role
- Event timestamp
- Source IP address
- API action
- Request parameters

Determine whether the change was expected and authorized.

### 4. Determine Risk

Evaluate whether the change creates unnecessary network exposure.

Pay particular attention to:

- `0.0.0.0/0`
- SSH — TCP 22
- RDP — TCP 3389
- Administrative services
- Sensitive application ports

Apply the principle of least privilege when determining whether access is necessary.

---

## Response Actions

### Authorized Change

If the change was expected and approved:

1. Document the investigation.
2. Confirm that the rule follows least-privilege principles.
3. Close the alert.

### Unauthorized or Unsafe Change

If the change was not authorized or introduces unnecessary exposure:

1. Remove or restrict the Security Group rule.
2. Preserve the CloudTrail event for investigation.
3. Identify the IAM principal responsible for the change.
4. Review additional activity performed by that identity.
5. Escalate the incident if suspicious activity is identified.
6. Document the remediation actions.

## Example Scenario

### Alert

```text
Severity: HIGH
Event: Inbound security group rule added
API Action: AuthorizeSecurityGroupIngress
Port: 22
Source: 0.0.0.0/0

```

### Analysis

SSH has been exposed to the entire public internet. This increases the attack surface of any resource associated with the Security Group.

### Response

The analyst should verify whether public SSH access was intentionally approved.

If it was not approved, the rule should be removed or restricted to an authorized IP range, VPN, bastion host, or other approved access path.

CloudTrail should then be reviewed to determine who made the change and whether additional suspicious activity occurred.

## Future Automation

Future versions of this project could automate portions of the response process, including:

- Automatically removing dangerous Security Group rules
- Quarantining affected resources
- Creating incident tickets
- Sending alerts to Slack or Microsoft Teams
- Generating AI-assisted incident summaries with Amazon Bedrock
- Recording incidents in DynamoDB
- Escalating repeated HIGH-severity events

---

## Security Principle

This monitoring workflow follows a core cloud security principle:

> Detect potentially dangerous configuration changes quickly, investigate the identity and context behind the change, and reduce unnecessary access using least privilege.
